# Точность данных и редакционная политика

## Состояния и доказательства

- Источник с высоким авторитетом не делает автоматически актуальными все данные на его сайте.
- Хранить наблюдение **по полю**: имя, значение, ссылка, фрагмент страницы/документа, время наблюдения, состояние проверки.
- `observed` означает «нашли в источнике», `verified` — «проверено редактором/организатором», `conflict` — источники расходятся. Не подменять эти состояния числом `trust: 5`.
- В starter по умолчанию проверка считается устаревшей через 3 дня, если старт в пределах 14 дней, и через 14 дней для дальних событий. Порог — конфигурационная политика, её надо калибровать по SLA организаторов.
- Не удалять и не переписывать подтверждённые значения без записи в журнале.

## Правила статуса

- Прошедшие даты сами по себе не доказывают, что событие состоялось: показывать «даты прошли, статус не подтверждён».
- `completed`, `cancelled` и `postponed` ставить только по подтверждённой публикации.
- Состояние регистрации (`open`, `closed`, `unknown`) хранить отдельно от состояния турнира.
- Победитель и итоговый счёт публикуются только по официальному протоколу или прямому подтверждению организатора.
- Конфликт дат/площадки/результата — ручная проверка; не выбирать «самое свежее» автоматически.

## Поток данных

1. Источник одобрен по условиям использования; указаны владелец и допустимая частота.
2. Сохраняются дата проверки, HTTP-код и хэш очищенного текста.
3. Коннектор извлекает кандидаты со ссылкой и точным фрагментом доказательства.
4. Нормализация дат, региона, спорта, категорий и URL; валидация `end >= start`.
5. Дедупликация выдаёт кандидатов, но не сливает неоднозначные события молча.
6. Редактор подтверждает новые и изменившиеся данные.
7. Публикация показывает дату проверки, источник и статус уверенности.

LLM допустима как помощник извлечения, но не как автор фактов. На вход модели давать только сохранённый документ; на выходе — схему и цитаты/смещения источника. Без подтверждаемого фрагмента факт остаётся неподтверждённым.

## Пример: HCP-группы, которые нельзя свести к одному диапазону

У одного турнира категории могут быть разными для мужчин и женщин. Не хранить это как общий `hcp_min=0, hcp_max=36`: такой диапазон ошибочно порекомендует событие, например, мужчине с HCP 33. Пока группы не представлены нормализованной структурой с категориями, хранить текст регламента, не делать вывод «ты точно подходишь» и показывать «сверь ограничения с регламентом».

## Защита сбора

- `robots.txt` проверять по каждому origin и кэшировать; 401/403/429/5xx и ошибка сети — отказ от сбора.
- Пустой/отсутствующий `robots.txt` не отменяет условия использования сайта.
- Контактный User-Agent, лимит тела ответа, таймауты, ограничение запросов, проверка перенаправлений.
- Автоматический сбор включать только явным `crawl_approved`; данный starter по умолчанию источники только мониторит/обрабатывает вручную.
